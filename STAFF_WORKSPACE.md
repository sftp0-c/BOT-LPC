# Кабинет сотрудников и рабочее место

Документ описывает локальную разработку 2.0.0. На сервере остаётся опубликованная
1.7.0, пока владелец отдельно не подтвердит выпуск. Сам файл `VERSION` до этого
подтверждения не меняется. Публичная главная сохранена без редизайна.

## Два независимых входа

- **Сис-админ:** прежний `/panel/login`, MAX ID и пароль панели.
- **Обычный сотрудник:** `/workspace/login`, MAX ID и одноразовый код в личном
  диалоге с ботом MAX. Ссылка есть на странице административного входа.

Для сотрудника используются существующие ФИО, должность и MAX ID из `admins`.
Новая регистрация профиля не создаётся. Само знание чужого MAX ID не даёт входа.

### Как дать доступ

1. Сначала заведите настоящего сотрудника в разделе «Сотрудники» или подтвердите
   его обычное приглашение/заявку в боте.
2. Откройте **«Доступ сотрудников»** (`/panel/staff-access`).
3. Найдите человека по ФИО, должности или MAX ID и нажмите «Настроить».
4. Включите доступ и выберите набор: «Только просмотр своих», «Работа со своими»
   или «Настроить отдельно».
5. Сохраните. Прежние веб-сеансы и ещё не использованные коды этого сотрудника
   отзываются; для входа потребуется свежий код.

Ни один существующий сотрудник не получает веб-доступ автоматически.
Тестовые профили и системные администраторы в список выдачи staff-доступа не входят.
Раздел защищён административной ролью; сотрудник не может выдать права себе.

## Что означают права

Включённый веб-доступ уже разрешает читать **назначенные человеку обращения**.
Связь определяется `tickets.target_admin_id == admins.user_id`, а не совпадением
ФИО, группы, отдела или категории.

| Право | Что разрешает |
|---|---|
| Ответы студентам | Сохранить и отправить ответ от имени текущего сотрудника |
| Смена статуса | Изменить статус разрешённого обращения |
| Внутренние заметки | Сохранить заметку для сотрудников, не отправляя студенту |
| Передача обращений | Передать вопрос действующему сотруднику подходящей категории |
| Шаблоны ответов | Подставить разрешённый шаблон в черновик, без автоматической отправки |
| Вложения | Скачать файл с подтверждённой связью с доступным обращением |
| Выгрузка CSV | Выгрузить только разрешённую очередь с текущими фильтрами, до 2000 строк |
| Просмотр чужих обращений | Читать другие обращения колледжа; не выдаёт право изменять их |
| Изменение чужих обращений | Допускает операции с чужими обращениями, но каждая операция всё равно требует своего права |

Набор **«Работа со своими»** включает ответы, статусы, заметки, передачу,
шаблоны и вложения. Выгрузка и работа с чужими обращениями выключены.
«Ответить и закрыть» требует одновременно прав ответа и смены статуса.

Это **права на сайте**, не права MAX. Старый `see_all_tickets` в боте не включает
веб-доступ и не заменяет новые флажки. Управление базой, людьми, ролями,
глобальными шаблонами, создание за студента и удаление обращений остаются у сис-админа.

## Как работать с обращениями

На компьютере слева очередь, справа выбранное обращение. На узком экране
карточка открывается без сжатой второй колонки; кнопка «К очереди» возвращает список.
Прямая ссылка `/workspace/tickets/<номер>` открывает карточку независимо от страницы очереди.

Вкладки **«Открытые»**, **«Ждут ответа»**, **«Закрытые»** находятся над поиском.
«К выдаче» относится к открытым. Архив — отдельный фильтр, архивные карточки
доступны для чтения без рабочих изменений. Дополнительные условия, даты,
категория и «Дольше суток» собраны в раскрываемых фильтрах.

Карточка содержит сведения об обращении, хронологию и поле ответа. Внутренняя
заметка явно отделена от ответа студенту. Передача и смена статуса находятся в
«Ещё действия». Шаблон сначала подставляется в черновик — его можно проверить
и исправить перед отправкой.

Черновик хранится только в `sessionStorage` текущей вкладки, раздельно по кабинету,
сотруднику, номеру обращения и режиму. Это не серверный архив текста. Перед уходом
с неотправленными изменениями браузер предупреждает. При недоступном хранилище
форма работает, но закрытие страницы может потерять неотправленный текст.

Старая форма не может молча изменить уже переданное обращение: сервер проверяет
актуальный доступ, назначение и числовую ревизию в транзакции. При конфликте
проверьте обновлённую карточку. Повтор того же POST не создаёт второй ответ.

### Отправка в MAX

Ответ сначала сохраняется в общей истории, затем вызывается API MAX. Если вызов
не подтвердился, интерфейс сообщает об этом отдельно. **Не нужно повторять сам
ответ ради доставки** — сохранённое сообщение уже существует.

Ответ API не является подтверждением прочтения. Персистентной очереди повторной
доставки в этой версии нет; после перезагрузки статус доставки старых сообщений
может оставаться «Доставка не подтверждена». Это не означает, что сообщение
обязательно не дошло.

## Безопасность входа

- Код из 8 цифр действует до 5 минут и только в исходном браузере; 5 ошибочных
  попыток погашают его. Временная browser-cookie действует 10 минут.
- Коды и сеансы не хранятся в открытом виде. Назначения HMAC разделены между
  кодом, браузером, CSRF и сеансом.
- Нейтральный ответ на запрос кода не раскрывает, существует ли заданный ID.
- Новая сессия сотрудника действует 12 часов, хранится на сервере и отзывается
  при выходе, изменении доступа, удалении/смене роли и переводе профиля в тестовый.
- Повторное добавление того же MAX ID не оживляет старые сеансы.
- Восстановление SQLite-копии очищает staff-сеансы и ожидающие коды в подготовленной
  копии **до** её переноса в живую базу; исходный резервный файл не меняется.
- Лимиты запросов/проверок действуют по браузеру, идентификатору и HMAC сетевого
  соседа. За общим reverse proxy сетевой лимит может быть общим для нескольких
  людей; `X-Forwarded-For` не считается источником личности.
- Нужен длинный `WEB_SESSION_SECRET` и правильный `PUBLIC_URL` с HTTPS на сервере.
  Ошибка конфигурации не обходится паролем сотрудников.
- Форма входа ограничена фактическими 8 КиБ, staff-формы — 64 КиБ до разбора.
  Проверяются CSRF, формат, повторы полей и Origin.

Административная сессия v1.7.0 остаётся прежней подписанной cookie. Новый серверный
отзыв здесь относится именно к кабинету сотрудников, а не объявляет задним числом
переработку всех административных сессий.

## Вложения

Новые файлы получают уникальное безопасное имя и запись `ticket_files`, связанную
с обращением и сообщением. Сотрудник скачивает по маршруту
`/workspace/tickets/<номер>/files/<id>`, где право проверяется ещё раз.

Строка «Файл: имя.pdf» в тексте не доказывает принадлежность. Старые вложения без
доверенной записи не выдаются сотруднику автоматически; в интерфейсе есть
предупреждение. Прежний административный маршрут сохранён. Автоматическая миграция
не угадывает принадлежность файла по произвольному сообщению.

## Где находится реализация

- `store/web_access.py` — OTP, сеансы, флажки и отзыв доступа.
- `web/workspace_auth.py` — формы входа, CSRF и проверки staff-сеанса.
- `web/staff_access.py` — административный экран выдачи веб-прав.
- `store/workspace.py` — единые проверки доступа, SQL-фильтры, атомарные операции,
  ревизии и доверенные вложения.
- `web/workspace.py` — маршруты, выгрузка, действия и изолированная оболочка staff.
- `web/workspace_view.py` — общая разметка рабочего места двух ролей, без БД.
- `web/static/workspace.css`, `workspace.js` — изолированный дизайн, черновики,
  предпросмотр шаблонов и живые таймеры.
- `web/tickets.py` — административные маршруты и старые операции. Расширенные
  редакторы вынесены на `/panel/tickets/<номер>/admin`, не вставлены в ежедневный ответ.
- `database.py` — аддитивные таблицы, триггеры ревизии/отзыва и безопасное восстановление.

`staff_web_*`, `workspace_operations` и доверенные связи файлов закрыты от сырого
редактора. Журналы получают коды действий, ID и имена полей, без OTP и переписки.

## Как проверять

Использовать временную SQLite и подмену всех сетевых методов MAX. Не подключать
дополнительный polling с боевым токеном и не выдавать доступ реальным сотрудникам
для тестового наполнения.

Целевые наборы: `test_workspace_auth`, `test_staff_web_access`,
`test_workspace_policy`, `test_workspace_files`, `test_workspace_routes`,
`test_workspace_view`. Полный допуск к выпуску:

```powershell
.\.venv\Scripts\python.exe -X utf8 -m pytest -q
.\.venv\Scripts\python.exe -m ruff check --select F,E9 .
```

Версия и сервер обновляются только после отдельного согласования. Тогда нужны
тег `v2.0.0`, обычный pre-push-хук, новый согласованный бэкап и проверка контейнера.
